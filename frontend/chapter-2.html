2.1.1 当日目标

学生先理解“等待网络时让出执行权”，再写并发。验收不是只看速度，而是能解释事件循环、协程、任务、并发限制和异常隔离。

2.1.2 用等待任务体感并发

import asyncio
from time import perf_counter


async def simulated_request(name: str, seconds: float) -> str:
    await asyncio.sleep(seconds)
    return f"{name} 完成"


async def main() -> None:
    started = perf_counter()
    results = await asyncio.gather(
        simulated_request("A", 1.0),
        simulated_request("B", 1.5),
        simulated_request("C", 0.5),
    )
    print(results)
    print(f"总耗时: {perf_counter() - started:.2f}s")


if __name__ == "__main__":
    asyncio.run(main())

逐层解释：

  1. 调用 async def 得到协程对象，await 才真正等待其完成。
  2. asyncio.sleep 模拟网络等待，它不会占住事件循环。
  3. gather 并发调度三个协程，总耗时接近最慢任务，而不是三者之和。
  4. 异步适合大量 I/O 等待，不会自动加速 CPU 密集计算。

2.1.3 统一配置与响应对象

from dataclasses import dataclass
import os


@dataclass(frozen=True)
class ProviderConfig:
    name: str
    base_url: str
    api_key: str
    model: str


@dataclass(frozen=True)
class ChatResult:
    text: str
    model: str
    provider: str
    prompt_tokens: int
    completion_tokens: int


def load_provider(prefix: str) -> ProviderConfig:
    values = {
        "base_url": os.getenv(f"{prefix}_BASE_URL", ""),
        "api_key": os.getenv(f"{prefix}_API_KEY", ""),
        "model": os.getenv(f"{prefix}_CHAT_MODEL", ""),
    }
    missing = [key for key, value in values.items() if not value]
    if missing:
        raise RuntimeError(f"{prefix} 缺少配置: {', '.join(missing)}")
    return ProviderConfig(prefix.lower(), **values)

统一对象让上层不依赖某家供应商的环境变量名和原始 JSON 结构。

2.1.4 异步 LLM 客户端

import httpx


class AsyncLLMClient:
    def __init__(self, config: ProviderConfig):
        self.config = config
        self.client = httpx.AsyncClient(
            base_url=config.base_url.rstrip("/"),
            headers={"Authorization": f"Bearer {config.api_key}"},
            timeout=httpx.Timeout(60.0, connect=10.0),
            limits=httpx.Limits(max_connections=20, max_keepalive_connections=10),
        )

    async def chat(self, messages: list[dict[str, str]]) -> ChatResult:
        response = await self.client.post(
            "/chat/completions",
            json={"model": self.config.model, "messages": messages, "temperature": 0.2},
        )
        response.raise_for_status()
        data = response.json()
        usage = data.get("usage") or {}
        return ChatResult(
            text=data["choices"][0]["message"]["content"],
            model=data.get("model", self.config.model),
            provider=self.config.name,
            prompt_tokens=int(usage.get("prompt_tokens", 0)),
            completion_tokens=int(usage.get("completion_tokens", 0)),
        )

    async def close(self) -> None:
        await self.client.aclose()

关键解释：

  • 客户端在应用生命周期内复用，才能利用连接池；不要在热点循环里反复创建。
  • raise_for_status() 将非成功 HTTP 状态变成明确异常。
  • 响应归一化后，上层只读取 ChatResult。
  • 日志不得输出 Authorization。

2.1.5 有上限的多供应商并发

async def compare_providers(clients: list[AsyncLLMClient], question: str, limit: int = 3) -> list[dict]:
    semaphore = asyncio.Semaphore(limit)

    async def ask_one(client: AsyncLLMClient) -> dict:
        async with semaphore:
            started = perf_counter()
            try:
                result = await client.chat([{"role": "user", "content": question}])
                return {"ok": True, "provider": result.provider, "text": result.text, "latency": perf_counter() - started}
            except Exception as exc:
                return {"ok": False, "provider": client.config.name, "error": type(exc).__name__, "latency": perf_counter() - started}

    return await asyncio.gather(*(ask_one(client) for client in clients))

Semaphore 保护本机连接池和上游额度。每个任务捕获自己的异常，避免一家失败导致整批结果丢失。

四条结论（必须理解，不只是看到数字）：

  1. 串行 3.64s → 并发 1.02s，加速 3.57 倍：等待时间可以被重叠，这是异步全部价值的来源；
  2. 并发的下界是「最慢的单任务」（1.00s），不是 0 —— 提高并发数不会让最慢的请求变快，

  2. 异步只对 I/O 等待有效。CPU 密集任务（本地推理、pandas 计算）要么丢进线程池/进程池，

要么接受它阻塞事件循环。

一个必须做的实验（<code>10_async_basics.py</code> 末尾）：

asyncio.sleep(0.5) × 2 并发 ：0.51s   ← 让出执行权，等待可以被重叠
time.sleep(0.5)    × 2 并发 ：1.00s   ← 独占事件循环，退化成串行

在协程里用 time.sleep() 会阻塞整个事件循环，所有并发全部失效。 这是新手最容易犯的性能错误——代码"看起来是异步的"，但性能等于同步。

异常隔离的要点：每个并发任务必须捕获自己的异常。 如果让异常逃逸到 gather，一家供应商失败会导致整批结果全部丢失。 图中演示了一个故意配错的供应商，验证其他供应商的结果不受影响。

q02-01-01（单选 · ★）gather 并发总耗时判断

用 asyncio.gather 并发调度三个协程，分别 await asyncio.sleep(1.0)、1.5、0.5 秒。 总耗时最接近下列哪个值？

  • A. 接近 1.5 秒，即最慢的那个任务
  • B. 接近 3.0 秒，即三者之和
  • C. 接近 0.5 秒，即最快的那个任务
  • D. 接近 0 秒，因为并发不消耗时间

答案：A

判分要点（AI 排错时逐条核对）

  • gather 并发调度多个协程
  • 等待时间可重叠
  • 总耗时≈最慢单任务
  • 并发下界不是 0

解析与常见错误：gather 把三个协程交给事件循环并发调度，等待时间被重叠，总耗时由最慢的任务决定，即 1.5 秒。三者之和 3.0 秒是串行的结果；0.5 秒是最快任务，不是总耗时；并发下界是最慢单任务而非 0。

q02-01-02（单选 · ★★）协程里误用 time.sleep

在协程中把 asyncio.sleep(0.5) 换成 time.sleep(0.5)，两个任务并发执行。 实测总耗时从 0.51s 变成 1.00s，原因是什么？

  • A. time.sleep 独占事件循环，不让出执行权，并发退化成串行
  • B. time.sleep 精度比 asyncio.sleep 低，产生了额外开销
  • C. time.sleep 会创建新线程，线程切换拖慢了整体速度
  • D. time.sleep 触发了连接池上限，请求被排队等待

答案：A

判分要点（AI 排错时逐条核对）

  • time.sleep 阻塞整个事件循环
  • 协程无法被调度
  • 并发退化为串行
  • 代码看似异步实则同步

解析与常见错误：time.sleep 是同步阻塞调用，会占住事件循环，其他协程无法在此期间被调度，于是两个 0.5 秒变成串行的 1.0 秒。它不创建线程，也与连接池无关，精度差异不足以解释翻倍耗时。这是新手最常见的性能错误。

q02-01-03（单选 · ★★）并发任务异常隔离

compare_providers 用 gather 并发请求多家供应商。 如果某个任务不捕获自身异常，让异常逃逸到 gather，会发生什么？

  • A. 一家供应商失败会导致整批结果全部丢失
  • B. 只有失败的那家返回错误，其余结果正常保留
  • C. gather 会自动重试失败的任务直到成功
  • D. 异常被静默忽略，失败任务返回空字符串

答案：A

判分要点（AI 排错时逐条核对）

  • 每个并发任务捕获自身异常
  • 异常逃逸 gather 丢失整批
  • 返回 ok/error 结构化结果
  • 故障注入验证隔离效果

解析与常见错误：异常逃逸到 gather 会让整批结果丢失，这正是要每个任务捕获自己异常的原因。正确做法是在 ask_one 内 try/except，返回 ok=False 与 error 字段，使其他供应商结果不受影响。gather 不会自动重试，也不会静默忽略异常。

q02-01-04（简答 · ★★）并发上限与理论下界

实测数据：串行 3.64s（1.00x，峰值并发 1）；无序并发 1.02s（3.57x，峰值并发 6）；限流并发 Semaphore=2 时 1.81s（2.01x，峰值并发 2）。 请解释：为什么提高并发数不能让总耗时低于最慢的单任务？为什么生产环境仍必须设并发上限？

提示：想想最慢那个请求本身要多久；连接池和上游额度都是有限资源

判分要点（AI 排错时逐条核对）

  • 总耗时下界是最慢单任务
  • 等待可重叠但单个请求不会变快
  • 无限并发峰值 6 连接，先被限流的是自己
  • Semaphore 保护连接池与上游额度
  • 限流版耗时 1.81s 接近理论下界 1.80s

解析与常见错误：关键是把「等待重叠」和「单个请求变快」区分开：并发只是让等待重叠，最慢任务本身耗时不变，所以总耗时下界就是它。提高并发数只会让请求排队，显得更慢。生产必须限流，否则本机连接池和上游额度先被打爆。

2.3.1 SSE 最小协议

SSE 由服务端通过一个长连接持续发送事件。每个事件以空行结束：

event: token
data: {"text":"你"}

event: done
data: {}

JSON 编码可避免换行和中文造成协议边界混乱。

2.3.2 解析上游流

import json
from collections.abc import AsyncIterator


async def stream_chat(client: AsyncLLMClient, messages: list[dict[str, str]]) -> AsyncIterator[str]:
    payload = {"model": client.config.model, "messages": messages, "stream": True}
    async with client.client.stream("POST", "/chat/completions", json=payload) as response:
        response.raise_for_status()
        async for line in response.aiter_lines():
            if not line.startswith("data:"):
                continue
            data = line.removeprefix("data:").strip()
            if data == "[DONE]":
                break
            chunk = json.loads(data)
            text = chunk["choices"][0].get("delta", {}).get("content")
            if text:
                yield text

离开 async with 后 HTTPX 自动关闭上游响应，避免连接泄漏。

2.3.3 向浏览器转发 SSE

from fastapi.responses import StreamingResponse


def sse(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"


@app.post("/chat/stream")
async def chat_stream(payload: ChatRequest, llm: AsyncLLMClient = Depends(get_llm)):
    messages = [message.model_dump() for message in payload.messages]

    async def events():
        try:
            async for token in stream_chat(llm, messages):
                yield sse("token", {"text": token})
            yield sse("done", {})
        except Exception:
            yield sse("error", {"message": "流式响应中断"})

    return StreamingResponse(events(), media_type="text/event-stream", headers={"Cache-Control": "no-cache"})

2.3.4 会话存储与上下文裁剪

import asyncio
from collections import defaultdict


class SessionStore:
    def __init__(self, max_messages: int = 20):
        self.max_messages = max_messages
        self.data: dict[str, list[dict[str, str]]] = defaultdict(list)
        self.lock = asyncio.Lock()

    async def append_turn(self, session_id: str, user_text: str, assistant_text: str) -> None:
        async with self.lock:
            history = self.data[session_id]
            history.extend([
                {"role": "user", "content": user_text},
                {"role": "assistant", "content": assistant_text},
            ])
            self.data[session_id] = history[-self.max_messages:]

    async def get(self, session_id: str) -> list[dict[str, str]]:
        async with self.lock:
            return list(self.data.get(session_id, []))

    async with client.client.stream("POST", "/chat/completions", json=payload) as response:

            if not line.startswith("data:"):
                continue

            if data == "[DONE]":
                break

            text = chunk["choices"][0].get("delta", {}).get("content")
            if text:

2.4.1 带退避的有限重试

import random


RETRYABLE_STATUS = {429, 500, 502, 503, 504}


async def call_with_retry(operation, attempts: int = 3):
    for attempt in range(1, attempts + 1):
        try:
            return await operation()
        except httpx.HTTPStatusError as exc:
            if exc.response.status_code not in RETRYABLE_STATUS or attempt == attempts:
                raise
        except (httpx.ConnectError, httpx.TimeoutException):
            if attempt == attempts:
                raise
        delay = min(4.0, 0.5 * 2 ** (attempt - 1)) + random.uniform(0, 0.2)
        await asyncio.sleep(delay)
    raise RuntimeError("不可达分支")

401、403 和大部分 400 错误不应重试；重试次数必须有限，并加入随机抖动，避免大量请求同时再次冲击上游。

2.4.2 进程内限流器

from collections import defaultdict, deque
from time import monotonic


class SlidingWindowLimiter:
    def __init__(self, limit: int, window_seconds: float):
        self.limit = limit
        self.window = window_seconds
        self.records: dict[str, deque[float]] = defaultdict(deque)
        self.lock = asyncio.Lock()

    async def allow(self, key: str) -> bool:
        now = monotonic()
        async with self.lock:
            queue = self.records[key]
            while queue and queue[0] <= now - self.window:
                queue.popleft()
            if len(queue) >= self.limit:
                return False
            queue.append(now)
            return True

多实例部署时进程内限流不共享状态，应迁移到网关或 Redis。key 可来自登录用户或可信网关传来的客户端标识，不能盲目信任任意请求头。

2.4.6 结构化输出：让模型只吐你能解析的东西

到这一步，你的后端已经能重试、能限流、能写日志。但还有一个地方在裸奔：模型的输出格式。

前面所有接口都假设模型会乖乖返回 JSON。真实情况是：它会加上 Markdown 围栏、会写注释、会在 JSON 后面补一句「希望对你有帮助」、会把 priority 填成 "高"。你的 json.loads 直接抛异常，前端拿到 500。

这一节把「模型输出」当成不可信输入来对待——和用户上传的文件同等对待。

三种约束强度，先建立正确的预期
强度做法模型不听话时适用
弱只在提示词里写「请返回 JSON」你承担全部后果一次性脚本、演示
中response_format={"type": "json_object"}保证是合法 JSON，但不保证符合你的 schema结构简单的场景
强response_format={"type": "json_schema", ...} 或工具调用的 schema上游尽力约束，仍要本地校验兜底生产接口、入库数据

关键认知：「强约束」也不是零风险。 不同供应商对 strict 模式的支持程度不同，长上下文下仍可能降级。所以生产代码的写法是固定的一条链：

能约束就约束  →  拿到就校验  →  校验失败就修复重试  →  仍失败就降级返回

少任何一环，异常都会漏到用户面前。

第二步：写一个能自我修复的解析器

核心思路：解析失败不是异常，而是一次「给模型第二次机会」的信号。把模型调用注入进来，这样它既能接真实 API，也能在测试里用假模型跑。

# code/ch02/d09/parse_with_repair.py
from __future__ import annotations

from typing import Callable

from pydantic import ValidationError

from structured_output import Ticket

REPAIR_TEMPLATE = (
    "你上一次的输出无法通过校验：{error}\n"
    "原始输出：\n{raw}\n\n"
    "只返回修复后的 JSON 对象，不要任何解释、不要 Markdown 围栏。"
)


def parse_with_repair(
    raw: str,
    call_model: Callable[[str], str],
    *,
    max_repair: int = 2,
) -> tuple[Ticket | None, list[str]]:
    "返回 (结果, 历史错误)。结果为 None 表示降级，调用方必须处理。"
    errors: list[str] = []
    for _ in range(max_repair + 1):
        try:
            return Ticket.model_validate_json(raw), errors
        except ValidationError as exc:
            first = exc.errors()[0]
            errors.append(f"{first['loc']}: {first['msg']}")
            raw = call_model(
                REPAIR_TEMPLATE.format(error=errors[-1], raw=raw[:2000])
            )
    return None, errors

四个细节值得单独说：

  • <code>max_repair=2</code> 是硬上限。 修复循环本质是重试，没有上限就是烧钱循环。两次仍失败说明任务本身不适合这个 schema。
  • 只把第一条错误回传给模型。 一次塞十条错误会让模型手忙脚乱，改对一条再谈下一条，收敛更快。
  • <code>raw[:2000]</code> 截断。 原始输出可能很长，全量回传会让修复请求瞬间吃掉上下文预算。
  • 返回 <code>None</code> 而不是抛异常。 降级路径由调用方决定：返回 422 给前端、写待人工处理队列、或退化成纯文本回复。

2.4.7 mypy 与类型工程：让错误在运行前暴露

你写的是 Python，但 Agent 项目最怕的就是「运行时才发现」。一个工具调用的参数名写错，可能要到线上第 300 次调用才暴露，而那时它已经在数据库里写脏了数据。

这一节把类型从「注释」变成「检查」。

为什么 Agent 项目比普通项目更需要类型
场景没有类型的后果
工具参数{"city_name": ...} 与 def f(city: str) 对不上，模型传的键名永远匹配不上
消息列表list[str] 与 list[dict] 混用，运行时才 TypeError
多供应商返回不同平台字段名不同，靠猜 result.text / result.content
上下文装配传错顺序不会报错，只会让模型回答变差——最难排查的一类 bug

静态类型检查的价值：把这几类错误从「用户先发现」变成「提交前发现」。

三类类型写法，从松到紧

第一类：联合类型与可选值

from typing import Literal

Role = Literal["system", "user", "assistant", "tool"]
FinishReason = Literal["stop", "length", "tool_calls", "content_filter"]


def parse_finish_reason(raw: str) -> FinishReason:
    allowed: tuple[FinishReason, ...] = ("stop", "length", "tool_calls", "content_filter")
    for item in allowed:
        if raw == item:
            return item
    return "stop"

Literal 比 str 严格得多：写 role="userr" 时 mypy 直接报错。Agent 项目的消息角色、工具状态、事件类型，都应该用 <code>Literal</code>。

第二类：TypedDict 描述消息体

from typing import TypedDict


class ChatMessage(TypedDict):
    role: Role
    content: str


def build_messages(system: str, user: str) -> list[ChatMessage]:
    return [
        {"role": "system", "content": system},
        {"role": "user", "content": user},
    ]

dict[str, str] 的问题在于「任何键都合法」；TypedDict 会检查键名和值类型。如果写成 {"roles": "user", "content": ...}，mypy 立刻报「缺少 role，多了 roles」。

第三类：Protocol 定义接口（Day 09 已用过）

from typing import Protocol


class ChatModel(Protocol):
    async def chat(self, messages: list[ChatMessage]) -> "ChatResult": ...

Protocol 的价值是结构化子类型：任何实现了 chat 的对象都自动满足它，不需要继承。Agent 项目里大量使用「鸭子类型」——这就是把它显式化的方式，也是你后面写测试时能塞假实现的基础。

pydantic v2：边界校验的运行时防线

类型注解是开发时的，pydantic 是运行时的。两者互补，缺一不可。

from pydantic import BaseModel, Field, field_validator


class ToolCallRequest(BaseModel):
    tool_name: str = Field(min_length=1, max_length=64)
    arguments: dict[str, object] = Field(default_factory=dict)
    timeout_s: float = Field(default=10.0, ge=0.1, le=60.0)

    @field_validator("tool_name")
    @classmethod
    def reject_unsafe_name(cls, v: str) -> str:
        if not v.replace("_", "").isalnum():
            raise ValueError("工具名只允许字母、数字与下划线")
        return v
try:
    req = ToolCallRequest(tool_name="query_weather", timeout_s=999)
except Exception as exc:
    print(exc)

输出会明确指出 timeout_s 超出上限（less than or equal to 60）。

为什么模型给的参数一定要过 pydantic：模型可能给出 timeout_s: "十秒"、tool_name: "../etc/passwd"、arguments: null。应用层手写 if 校验既啰嗦又容易漏，pydantic 一行覆盖，而且错误信息可以直接回灌给模型让它重试（Day 03 讲过的校验重试链路）。

2.4.8 用 pytest 证明你的代码是对的

到 Day 09 为止，你写的每个功能都靠「手动跑一遍，看到输出对了」来确认。这种方式在面试里一文不值，因为面试官无法验证，你自己下周改代码时也无法确认有没有改坏。

这一节把「我觉得能跑」换成「一跑就知道」。

为什么必须是自动化测试
手动验证自动化测试
每次改动都要重新点一遍uv run pytest -q 三秒给出结论

q02-04-01（单选 · ★）哪些错误不该重试

调用 LLM API 时收到以下响应，哪一类重试一次也不可能成功？

请选出最准确的判断标准。

  • A. 401 密钥错误与 400 参数错误
  • B. 429 限流与 503 上游过载
  • C. 连接超时与读取超时
  • D. 502 与 504 网关错误

答案：A

判分要点（AI 排错时逐条核对）

  • 只重试瞬时错误：429/5xx/连接超时
  • 401、403 与大部分 400 不重试
  • 判断标准：重试一次有可能成功吗
  • 确定性错误重试只浪费配额

q02-04-02（单选 · ★★）退避延迟的计算

重试退避公式为：

delay = min(4.0, 0.5 * 2 ** (attempt - 1)) + random.uniform(0, 0.2)

当 attempt = 1 时，delay 的取值范围是？

  • A. 0.5 秒到 0.7 秒之间
  • B. 0.5 秒到 4.0 秒之间
  • C. 1.0 秒到 1.2 秒之间
  • D. 0 秒到 0.2 秒之间

答案：A

判分要点（AI 排错时逐条核对）

  • attempt=1 时指数项为 0.5
  • min(4.0, ...) 封顶 4 秒
  • 抖动 uniform(0, 0.2) 叠加
  • 抖动防止重试风暴

解析与常见错误：attempt=1 时 0.5 * 2**0 = 0.5，min(4.0, 0.5) = 0.5，再加 random.uniform(0, 0.2)，所以落在 0.5~0.7 秒。指数部分随 attempt 翻倍，到 attempt=4 时被 min 截断在 4.0。抖动是叠加项，不是替代项。

  • B. 保持不变，因为限流器按 key 分桶
  • C. 变成约 4 倍，应把 limit 除以 4 写死

解析与常见错误：进程内限流器的 records 与 lock 都在单个进程内存里，多实例各算各的，总速率近似按实例数放大。asyncio.Lock 只保护本进程协程，不跨进程。正确做法是把限流迁到网关或 Redis，而不是把 limit 写死除以实例数。

import asyncio
import random
import httpx

RETRYABLE_STATUS = {429, 500, 502, 503, 504}

async def call_with_retry(operation, attempts: int = 3):
    for attempt in range(1, attempts + 1):
        try:
            return await operation()
        except httpx.HTTPStatusError as exc:
            if exc.response.status_code not in RETRYABLE_STATUS or attempt == attempts:
                raise
        except (httpx.ConnectError, httpx.TimeoutException):
            if attempt == attempts:
                raise
        delay = min(4.0, 0.5 * 2 ** (attempt - 1)) + random.uniform(0, 0.2)
        await asyncio.sleep(delay)
    raise RuntimeError("不可达分支")

from collections import defaultdict, deque
from time import monotonic
import asyncio

class SlidingWindowLimiter:
    def __init__(self, limit: int, window_seconds: float):
        self.limit = limit
        self.window = window_seconds
        self.records: dict[str, deque[float]] = defaultdict(deque)
        self.lock = asyncio.Lock()

    async def allow(self, key: str) -> bool:
        now = monotonic()
        async with self.lock:
            queue = self.records[key]
            while queue and queue[0] <= now - self.window:
                queue.popleft()
            if len(queue) >= self.limit:
                return False
            queue.append(now)
            return True

import asyncio
from statistics import median
from time import perf_counter
import httpx

async def one_request(client: httpx.AsyncClient, index: int) -> dict:
    started = perf_counter()
    response = await client.post("/chat", json={
        "messages": [{"role": "user", "content": f"用一句话解释异步编程，编号 {index}"}]})
    return {"status": response.status_code, "latency": perf_counter() - started}

async def load_test(total: int = 20) -> None:
    async with httpx.AsyncClient(base_url="http://127.0.0.1:8000", timeout=90) as client:
        rows = await asyncio.gather(*(one_request(client, i) for i in range(total)))
        latencies = sorted(row["latency"] for row in rows)
        p95 = latencies[max(0, int(len(latencies) * 0.95) - 1)]
        print({
            "total": total,
            "success": sum(row["status"] == 200 for row in rows),
            "median_seconds": round(median(latencies), 3),
            "p95_seconds": round(p95, 3),
            "statuses": {code: sum(row["status"] == code for row in rows)
                         for code in sorted({row["status"] for row in rows})},
        })

if __name__ == "__main__":
    asyncio.run(load_test())

from fastapi import FastAPI, UploadFile, File, HTTPException
import uuid, os

app = FastAPI()
UPLOAD_DIR = "data/uploads"
MAX_SIZE = 5 * 1024 * 1024
ALLOWED = {".txt", ".md", ".pdf"}

@app.post("/upload")
async def upload(file: UploadFile = File(...)):
    ext = os.path.splitext(file.filename or "")[1].lower()
    if ext not in ALLOWED:
        raise HTTPException(status_code=415, detail="unsupported file type")
    content = await file.read()
    if len(content) > MAX_SIZE:
        raise HTTPException(status_code=413, detail="file too large")
    os.makedirs(UPLOAD_DIR, exist_ok=True)
    file_id = uuid.uuid4().hex + ext
    with open(os.path.join(UPLOAD_DIR, file_id), "wb") as f:
        f.write(content)
    return {"file_id": file_id, "size": len(content)}
