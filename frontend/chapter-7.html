7.1.1 教学目标

  1. 说清 MetaGPT 的核心设计思路：把软件公司的 SOP 编码成 Agent 协作流程；
  2. 理解 Role / Action / Environment / Message 四个核心抽象的分工；
  3. 能对照第 6 章的三种协作模式，判断 MetaGPT 属于哪一类。

7.1.2 核心设计思路

MetaGPT 的出发点是一个观察：软件团队之所以能协作，是因为有 SOP（标准作业程序）—— 产品经理写 PRD，架构师据此设计，工程师实现，测试验证。每一步的输入输出格式是约定的。

所以 MetaGPT 做的事情是：

把「岗位职责 + 交付物格式」编码成 Agent 的 Role 和 Action
    ↓
用一个共享的消息池（Environment）让各角色按 SOP 顺序消费和产出
    ↓
于是「多智能体协作」变成了「消息驱动的流水线」

这个设计的关键洞察：多 Agent 协作的难点不是「让模型扮演角色」（那只是改 system prompt）， 而是「保证角色之间的接口稳定」——PRD 的结构必须让架构师能读懂，架构图必须让工程师能实现。 MetaGPT 用结构化的交付物 Schema 解决了这个问题。

对照第 6 章：MetaGPT 本质上是流水线模式（Day26 的模式一）， 但它比我们课堂上的版本严格得多——它给每个环节定义了强制的输出结构。

7.1.3 四个核心抽象

抽象职责对应你手写过的什么
<code>Role</code>一个岗位。持有 goal、约束、可执行的 Action 列表第 4 章的 Agent + system prompt
<code>Action</code>一个可执行的原子动作（写 PRD、画图、写代码）第 4 章的 Tool，但更重：它有自己的 prompt 模板和输出解析
<code>Environment</code>共享的消息空间与调度器第 6 章 Manager 的「任务分派」部分
<code>Message</code>结构化消息（带角色、内容、元数据）第 4 章的 messages 数组，但结构化程度高得多

<code>Role</code> 与 <code>Action</code> 的分离是设计要点：

# 简化示意（不是真实源码，用于说明结构）
class Role:
    goal: str                    # 这个岗位的目标
    actions: list[Action]        # 它能做哪些动作
    watch: set[MessageType]      # 它关心哪些消息

class Action:
    name: str
    prompt_template: str         # 这个动作的提示词（含 Few-shot 示例）
    output_schema: type          # 输出的结构（Pydantic 模型）
    async def run(self, context) -> Message: ...

为什么这样切分：

  • 一个 Role 可以有多个 Action（架构师既能设计模块，也能评审）；
  • 一个 Action 可以被多个 Role 复用（「写文档」这个动作产品经理和架构师都要做）；
  • output_schema 是接口契约——这是让流水线能自动串起来的关键。

解析与常见错误：思路是把 MetaGPT 的流水线抽象压缩成：共享消息池 + 顺序角色 + Schema 校验。关键点是下游只读上一条消息，形成单向数据流；校验失败重试一次再抛异常，对应教材提到的解析失败处理问题。常见错误是让角色并发执行破坏顺序，或校验失败直接静默跳过，导致下游拿到残缺输入。

class Message:
    def __init__(self, role, content):
        self.role = role
        self.content = content

class Action:
    def __init__(self, name, schema, fn):
        self.name = name
        self.schema = schema
        self.fn = fn

    def run(self, ctx):
        out = self.fn(ctx)
        for k in self.schema:
            if k not in out:
                raise ValueError(f"missing {k}")
        return out

class Pipeline:
    def __init__(self, roles, env):
        self.roles = roles
        self.env = env

    def run(self, idea):
        self.env.append(Message("user", {"idea": idea}))
        for role in self.roles:
            ctx = self.env[-1].content
            last_err = None
            for _ in range(2):
                try:
                    out = role.action.run(ctx)
                    self.env.append(Message(role.name, out))
                    last_err = None
                    break
                except ValueError as e:
                    last_err = e
            if last_err is not None:
                raise RuntimeError(f"{role.name} failed: {last_err}")
        return self.env

def validate(payload, schema):
    missing = []
    type_errors = []
    for field, expected in schema.items():
        if field not in payload:
            missing.append(field)
            continue
        if not isinstance(payload[field], expected):
            type_errors.append(field)
    return missing, type_errors

7.2.9 LangFlow 的组件模型与 1.12 的 lfx 重构

为什么要讲这次重构：它是「抽象层如何演进」的活教材，也是答辩时能拉开差距的细节。

langflow 1.12 把核心能力抽成了一个独立的 pip 包 <code>lfx</code>： 源码位置从 src/backend/base/langflow/... 迁到了 src/lfx/src/lfx/...。 你在网上翻旧文章时会看到 langflow/custom/custom_component/component.py——它现在只是向后兼容的转发层，真正的实现在 lfx 里。

对你的直接影响：写自定义组件时从 <code>lfx</code> 导入，而不是从 <code>langflow</code> 导入。

from lfx.custom import Component
from lfx.inputs.inputs import BoolInput, DropdownInput, HandleInput, MessageTextInput

一个最小组件骨架：

from lfx.custom import Component
from lfx.inputs.inputs import MessageTextInput
from lfx.schema import Message


class UppercaseComponent(Component):
    display_name = "Uppercase"
    description = "把输入文本转成大写，演示自定义组件的最小结构"
    icon = "type"

    inputs = [
        MessageTextInput(name="text", display_name="文本", required=True),
    ]

    def build(self) -> Message:
        return Message(text=self.text.upper())

读这个骨架的三个要点：

  1. inputs 声明了组件在画布上要渲染哪些输入控件——画布 UI 是数据驱动的，不是手画的；
  2. build() 是执行入口，返回值沿连线流向下游；
  3. display_name / description / icon 是给用户在画布上看的元数据。
为什么这个设计值得学：它把「前端表单、后端执行、类型校验」三件事统一到了一份声明里。 第 9 章的毕业项目里要做「可配置的 Agent 能力」，可以直接借用这个思路。

关于 MCP：LangFlow 同时支持 MCP——既能作为 MCP Client 去连外部 MCP Server，也能把画布上的流暴露成 MCP Server。 对照 7.2.4 里 Dify 的 Integration 辨析，你现在应该能自己回答：「LangFlow 的组件机制和 MCP 是竞争关系吗？」

def validate_workflow(wf):
    nodes = wf.get("nodes", [])
    edges = wf.get("edges", [])
    errors = []
    ids = {n["id"] for n in nodes}
    for e in edges:
        if e["source"] not in ids:
            errors.append(f"unknown source: {e['source']}")
        if e["target"] not in ids:
            errors.append(f"unknown target: {e['target']}")
    adj = {i: [] for i in ids}
    for e in edges:
        if e["source"] in adj and e["target"] in ids:
            adj[e["source"]].append(e["target"])
    WHITE, GRAY, BLACK = 0, 1, 2
    color = {i: WHITE for i in ids}
    def dfs(u):
        color[u] = GRAY
        for v in adj[u]:
            if color[v] == GRAY:
                return True
            if color[v] == WHITE and dfs(v):
                return True
        color[u] = BLACK
        return False
    for i in ids:
        if color[i] == WHITE and dfs(i):
            errors.append("cycle detected")
            break
    return (len(errors) == 0, errors)

import re

VER_RE = re.compile(r"^\d+\.\d+\.\d+$")

def check_manifest(m):
    errors = []
    name = m.get("name")
    if not isinstance(name, str) or not name.strip():
        errors.append("invalid name")
    version = m.get("version")
    if not isinstance(version, str) or not VER_RE.match(version):

    api = m.get("api_version")
    if api not in SUPPORTED_API:
        errors.append("unsupported api_version")
    return (len(errors) == 0, errors)

7.3.2 从「调用工具」到「执行代码」的跳跃

第 4 章的工具调用是这样的：模型输出 {"name": "get_weather", "arguments": {...}}， 你的程序校验参数、执行函数、返回结果。风险是可控的——因为可执行的函数是你预先注册的。

Code Agent 是另一回事：模型生成一段代码，你去执行它。

维度工具调用（第 4 章）代码执行（Code Agent）

所以 Code Agent 的核心工程问题是沙箱，不是提示词。

7.3.3 沙箱的层次

层次手段隔离强度代价
1限制可导入模块（import 白名单）弱低（容易被绕过）
2子进程 + 超时 + 资源限制中中
3容器（Docker）+ 无网络 + 只读挂载较强中高
4虚拟机 / 微虚拟机强高
5独立机器 / 云沙箱服务最强最高

必须记住的一条：任何依赖「在同一个进程里跑 Python 并拦截危险操作」的方案都不是安全边界。 Python 的动态特性决定了这类拦截可以被绕过。真正的边界必须是操作系统级或进程级的。

沙箱除了安全，还要解决：

  1. 状态隔离：多次执行之间是否共享文件系统？不隔离会互相污染；
  2. 依赖管理：模型装的包会不会破坏宿主环境？
  3. 超时与资源：一个死循环会占满 CPU；
  4. 可复现：同样的任务两次执行，环境是否一致。

class LongTask:
    def __init__(self, workdir):
        self.workdir = workdir
        os.makedirs(workdir, exist_ok=True)
        self.state_path = os.path.join(workdir, "state.json")
        self.steps = []
        self.done = 0
        self.cancelled = False

    def add_step(self, name):
        self.steps.append(name)

    def _save(self):
        with open(self.state_path, "w") as f:
            json.dump({"steps": self.steps, "done": self.done}, f)

    def run(self):
        while self.done < len(self.steps):
            if self.cancelled:
                print("cancelled at step", self.done)
                break
            name = self.steps[self.done]
            with open(os.path.join(self.workdir, f"out_{self.done}.txt"), "w") as f:
                f.write(f"result of {name}")
            self.done += 1
            self._save()

    def cancel(self):
        self.cancelled = True

    def load(self):
        if os.path.exists(self.state_path):
            with open(self.state_path) as f:
                s = json.load(f)
            self.steps = s["steps"]
            self.done = s["done"]

import subprocess, sys

def run_code(code, timeout=5):
    try:
        p = subprocess.run(
            [sys.executable, "-c", code],
            capture_output=True, text=True, timeout=timeout
        )
        return {"timeout": False, "returncode": p.returncode,
                "stdout": p.stdout, "stderr": p.stderr}
    except subprocess.TimeoutExpired as e:
        return {"timeout": True, "returncode": None,
                "stdout": e.stdout or "", "stderr": e.stderr or ""}

if __name__ == "__main__":
    print(run_code("print(1+1)"))
    print(run_code("while True: pass", timeout=1))

也就是说：这条轨迹里有模型服务造成的偏差（第 2、3 步的形态不是真实模型的行为），但「工具真的被执行」和「环检测真的拦住了重复调用」这两点都是真实的。 读真实输出时必须能区分「哪些是框架的能力、哪些是模型服务的局限」。

q07-04-01（单选 · ★）分层设计的判断标准

在迷你 Agent 框架中，判断抽象是否合理的「最实用标准」是什么？

  • A. 加一个新功能需要改动的文件数量是否集中在一层
  • B. 框架总代码行数是否控制在百行级别
  • C. 每一层是否都使用了抽象基类
  • D. 分层数量是否与 LangChain 保持一致

答案：A

判分要点（AI 排错时逐条核对）

  • 变化点应隔离在单层
  • 加功能只改一处即为好抽象
  • 改三个文件说明分层划错
  • 比任何设计原则都直接

解析与常见错误：正文明确指出：「如果你发现加一个新功能需要改三个文件，说明分层划错了」，即变化点应被隔离在单层里。行数、抽象基类、与 LangChain 对齐都不是判断标准，分层数量也不是越多越好。

q07-04-02（单选 · ★★）@tool 装饰器的核心价值

@tool 装饰器从函数签名自动生成 JSON Schema，而不是让用户手写 Schema。 这样做的根本原因是什么？

  • A. 手写 Schema 无法表达嵌套对象类型
  • B. 避免函数签名与 Schema 双重维护导致的不一致
  • C. 装饰器生成的 Schema 体积更小、传输更快
  • D. 只有装饰器才能读取 docstring 的 Args 段

答案：B

判分要点（AI 排错时逐条核对）

  • 手写 Schema 存在双重维护
  • 签名成为唯一事实源
  • 避免模型传参与函数不匹配
  • 读类型标注与 Args 描述

解析与常见错误：正文指出手写 Schema 有「双重维护」问题：改了签名忘了改 Schema，就会出现「模型按 Schema 传参、函数不认」的诡异 bug。装饰器让签名成为唯一事实源。其余选项都不是正文给出的理由。

q07-04-03（单选 · ★★★）轨迹中哪些是真实能力

执行轨迹显示：第 1 步模型请求 calculator 并返回 399；第 2 步又请求同一工具，被环检测拦下；第 3 步输出一段通用回答。 关于这条轨迹，下列判断正确的是？

  • A. 第 3 步的通用回答证明模型具备真实推理能力
  • B. 第 2 步的重复调用是真实模型的标准行为
  • C. 工具真的被执行、环检测真的拦住重复调用，这两点真实
  • D. 整条轨迹都是模型偏差，不能作为框架能力的证据

答案：C

判分要点（AI 排错时逐条核对）

  • 第 1 步工具真实执行返回 399
  • 第 2 步环检测真实拦截
  • 第 2、3 步形态偏离理想路径，属模型或配置造成的偏差
  • 真实平台第 2 步应输出最终答案

解析与常见错误：正文强调：轨迹里第 2、3 步的形态偏离理想路径，属模型或配置造成的偏差，但「工具真的被执行」和「环检测真的拦住了重复调用」这两点都是真实的。读输出必须能区分框架能力与模型能力边界。

q07-04-05（简答 · ★★）记忆策略的取舍与可替换性

同一个 Agent 做 6 轮对话，BufferMemory(20) 上下文 20 条、估算 440 token；BufferMemory(4) 上下文 3 条、估算 100 token；SummaryMemory 上下文更少却能把早期信息带到最后一轮。 请分析这三种策略各自的代价，并说明「换记忆策略只改一个参数」为什么是好抽象的体现。

提示：对比条数、token、信息保留三方面；注意摘要不是免费的

判分要点（AI 排错时逐条核对）

  • BufferMemory 保留最近 N 条，简单但丢早期信息
  • BufferMemory(4) 丢掉了「我叫张伟」
  • SummaryMemory 省 token 但有损

from abc import ABC, abstractmethod

class Message:
    def __init__(self, role, content):
        self.role = role
        self.content = content

class Memory(ABC):
    @abstractmethod
    def add(self, message: Message) -> None:
        ...

    @abstractmethod
    def get_context(self) -> list:
        ...

class BufferMemory(Memory):
    def __init__(self, max_size: int = 20):
        self.max_size = max_size
        self._messages = []

    def add(self, message: Message) -> None:
        self._messages.append(message)
        if len(self._messages) > self.max_size:
            self._messages = self._messages[-self.max_size:]

    def get_context(self) -> list:
        return list(self._messages)

class SummaryMemory(Memory):
    def __init__(self, threshold: int = 4, summarize=None):
        self.threshold = threshold
        self.summarize = summarize or (lambda msgs: "摘要:" + "/".join(m.content for m in msgs))
        self._summary = None
        self._recent = []

    def add(self, message: Message) -> None:
        self._recent.append(message)
        if len(self._recent) > self.threshold:
            overflow = self._recent[:-self.threshold]
            merged = ([Message("system", self._summary)] if self._summary else []) + overflow
            self._summary = self.summarize(merged)
            self._recent = self._recent[-self.threshold:]

    def get_context(self) -> list:
        head = [Message("system", self._summary)] if self._summary else []
        return head + list(self._recent)

import time

class RunResult:
    def __init__(self):
        self.steps = []
        self.stop_reason = None
        self.llm_calls = 0
        self.tool_calls = 0
        self.elapsed_ms = 0.0

class Runner:
    def run(self, agent, task, max_steps: int = 10, timeout: float = 60) -> RunResult:
        result = RunResult()
        start = time.time()
        for i in range(1, max_steps + 1):
            if (time.time() - start) > timeout:
                result.stop_reason = "timeout"
                break
            t0 = time.time()
            try:
                step = agent.step(task)
            except Exception as exc:
                result.steps.append({
                    "index": i, "type": "error",
                    "ms": round((time.time() - t0) * 1000, 1),
                    "summary": str(exc),
                })
                result.stop_reason = "error"
                break
            ms = round((time.time() - t0) * 1000, 1)
            result.steps.append({
                "index": i, "type": step.get("type"),
                "ms": ms, "summary": step.get("summary", ""),
            })
            if step.get("type") == "llm":
                result.llm_calls += 1
            elif step.get("type") == "tool":
                result.tool_calls += 1
            if step.get("done"):
                result.stop_reason = "done"
                break
        else:
            result.stop_reason = "max_steps"
        result.elapsed_ms = round((time.time() - start) * 1000, 1)
        return result
