Day 26｜三种多智能体协作模式

≈120 分钟 7 道练习

6.1.1 教学目标

  1. 说清流水线、辩论式、Manager 统筹三种模式的适用条件与代价；
  2. 实现三种模式的最小可运行 Demo；
  3. 能根据任务特征选择模式，而不是凭偏好。

6.1.2 模式一：流水线（Planner → Executor → Reviewer）

结构：角色固定，顺序固定，前一个的输出是后一个的输入。

用户需求 → [Planner] → 计划 → [Executor] → 产出 → [Reviewer] → 终稿
                                    ↑                    │
                                    └────── 退回修改 ─────┘

适用：任务可以清晰拆成「规划 → 执行 → 校验」三段，且每段的判定标准不同。 典型场景：文档撰写、方案设计、代码生成 + 审查。

关键设计点：

设计点做法为什么
中间产物要落盘每个阶段的输出单独保存出错时能判断是规划错、执行错还是审校错
Reviewer 要有明确标准用确定性规则而不是「你觉得好不好」让审校可测试、可复现
修改次数要有上限max_revisions 写进状态防止 Planner↔Reviewer 无限循环

代价：LLM 调用次数 ≈ 阶段数 × (1 + 平均修改轮数)。比单 Agent 贵 2–4 倍。

6.1.3 模式二：辩论式（Debate）

结构：两个（或多个）Agent 持不同立场，第三个 Agent 做裁判。

提案 → [正方 Agent] ←→ [反方 Agent] → 裁判 Agent → 结论
            ↑  至少 2 轮交锋  ↑

适用：需要在多个合理方案间做取舍的决策。典型场景：技术选型、方案评审、风险评估。

为什么辩论有效：单 Agent 容易「自我确认」——它提出一个方案后，倾向于论证自己是对的。引入一个明确持反对立场的 Agent，能逼出被忽略的风险。

关键设计点：

  • 反方 Agent 的 system prompt 必须真的要求它反对，不能是「请给出不同意见」这种软要求；
  • 裁判 Agent 必须被要求指出双方各自最强的论据，不能简单站队；
  • 辩论轮次要有限（通常 2–3 轮），超过后收益递减而成本线性上升。

代价：调用次数 = 轮数 × 2 + 1。两轮辩论就是 5 次调用。

6.1.4 模式三：Manager 统筹（Manager-Worker）

结构：一个 Manager 负责拆解任务、分派给合适的 Worker、汇总结果。

用户任务 → [Manager] → 拆解为子任务
                ├→ [Worker A] ─┐
                ├→ [Worker B] ─┤→ [Manager 汇总] → 最终结果
                └→ [Worker C] ─┘

适用：任务规模不确定，子任务数量需要运行时决定。典型场景：研究报告（需要查多少个来源取决于问题）、数据分析（需要几步清洗取决于数据质量）。

关键设计点：

  • Manager 必须输出结构化的子任务列表（JSON），否则无法程序化分派；
  • 必须有子任务数量上限和总步数上限（这是 Manager 模式最容易失控的地方）；
  • Worker 之间不共享上下文（只共享 Manager 分派的任务描述），这是优点也是限制。

6.1.5 模式的学术出处（答辩时会被追问）

课堂上说的「流水线 / 辩论式 / Manager 统筹」是教学归纳命名，不是官方术语。你应当知道它们各自对应的权威出处：

本课命名权威出处关键原文/概念
流水线（Planner→Executor→Reviewer）Anthropic《Building effective agents》(2024-12-19) 提出的 Prompt chaining 与 Evaluator-optimizer；Plan-and-Solve 论文 (arXiv 2305.04091)；Reflexion (arXiv 2303.11366)Evaluator-optimizer："one LLM call generates a response while another provides evaluation and feedback in a loop"
Manager 统筹Anthropic《How we built our multi-agent research system》(2025-06-13) 的 orchestrator-worker 模式；AutoGen 的 GroupChatManager；CrewAI 的 Hierarchical ProcessAnthropic 原文："a lead agent coordinates the process while delegating to specialized subagents that operate in parallel"；CrewAI 原文："Tasks are not pre-assigned; the manager allocates tasks to agents based on their capabilities"
辩论式Du et al.《Improving Factuality and Reasoning in Language Models through Multiagent Debate》(arXiv 2305.14325, 2023-05-23)多智能体多轮辩论后收敛答案，提升事实性与推理

Anthropic 那个报告里有两个数字必须记住（这是答辩和面试的高频考点）：

  1. 多 Agent 系统的 token 消耗约为普通对话的 15 倍；
  2. token 使用量本身就解释了性能差异的约 80% —— 换句话说，多 Agent 的收益很大程度来自「花了更多算力去探索」，而不是「架构本身更聪明」。
结论直接指导选型：Anthropic 自己明确指出，多 Agent 不适合需要共享上下文的领域（例如多数编码任务）。 因为多 Agent 的核心代价是上下文被切分——每个 subagent 只看到一部分信息。 当任务强依赖全局一致性时，这个代价会超过收益。

流水线这张图要看「契约化」三个字怎么落地：

（1）不是三个模型，是三套职责约束。 图上第一句话就点明：三个角色共用同一个 LLM 客户端，靠不同的 system prompt 区分身份——「这正是『多智能体』最朴素也最实用的实现方式：不是三个模型，是三套职责约束。」

角色配置表给了每个角色的可调工具、职责边界和失败时的影响：

角色可调工具职责边界失败时的影响
Planner否只拆环节，不给答案和数字计划崩 → 后续全偏（最严重）
Executor是（每个子问题只给相关工具）检索 / 计算 / 查数据，给结论结论错误 → Reviewer 拦下

（2）Planner 的产出必须是结构化契约，不是一段自然语言计划。 图中 Planner 的 LLM 思考区（原文，仅供参考）里写着「当前知识库中没有足够依据」，但真正决定流程走向的是由代码分解出的 4 条子问题契约（Q1-Q4，每条含绑定工具、是否需个人数据、预期依据）。图上把这条设计原则写得很清楚：

拆解结果必须是结构化契约（子问题 + 工具 + 验收断言），而不是一段自然语言计划——只有契约才能被 Executor 执行、被 Reviewer 校验。LLM 的思考作为背景保留，但流程走向由契约决定。这就是「混合规划」。

（3）朴素做法要故意留一轮，好让真实缺陷暴露。 图上标明「第一轮刻意采用『模型自己决定调什么工具』的朴素做法，好让它的真实缺陷暴露出来」。截图里能看到模型服务的局限：[executor.Q1] 模型服务重复请求了同一个工具，已去重并关闭 tools 以收效（真实模型不会出现这一步）——这类模型服务特有的噪声必须在讲义里标注清楚，否则学生会以为是自己写错了。

（4）成本要按角色归因。 全流程成本汇总表按阶段列出 LLM 调用、工具调用、prompt / completion token 与耗时，合计 20 次 LLM 调用、5489 tokens；后面还给了各角色 token 占比条形图（executor.Q3 占 35.2% 最高，planner 仅 3.4%）。图上强调这件事的用途：中间产物要落盘、token 要分角色统计，才能定位错误来自哪一环。

（5）什么时候该用流水线。 图末的结论给出了适用 / 不适用的判断，以及三条工程纪律：契约先行（拆解结果要结构化，别用自然语言当接口）、代码管数据键（个人数据必须由代码带着键去查）、审校混合（能代码判的绝不用模型判，模型的判断降级为建议，不决定流程）。

但结论也必须如实报：2/4 次交锋被验证通过，其余未能命中指定主张——说明编排生效但不完整，生产环境应当对这个比例设置告警阈值。

（2）适用边界与两个硬前提。 辩论适合「决策没有唯一正确答案、需要权衡取舍」的场景（技术选型、架构评审、方案定标），不适合有客观正确答案的问题（算数、查制度——那应该调工具，不是辩论），也不适合需要快速出结论的场景（成本是流水线的 2 倍以上，见 40 号脚本实测）。

两个硬前提缺一个就退化成复读机：必须把对方上一轮的原文作为对话历史传进去，并强制「先引用再反驳」；必须有裁判，且裁判有权做「部分采纳」（二元判定会浪费双方的合理部分）。

（3）本文件的局限（如实说明，比结论更重要）。 这一节是整张截图中教学价值最高的部分：

  • 「交锋验证」是关键词匹配，不等于语义理解：模型可能用了同义词而没命中。所以它给出的是「有据可查的交锋」，不是「语义上真正被驳倒了」。升级方向是用 embedding 算语义相似度（第 3 章的能力复用）。
  • 裁判与辩手是同一个模型，存在「被措辞带偏」的风险。生产环境应当换模型或换厂商做裁判，并做裁判一致性评测。
  • 模型服务的能力边界（必须如实说明）：code/common/llm.py 是规则驱动的真实模型服务，它按关键词检索内置语料、再套人设模板生成回答，不具备链式推理能力，也无法真正「引用对方论点后反驳」。因此本次运行的实测结果是：

图上给这条设计一个精确的命名：这就是「把模型放在不可靠的位置上不值得」——应对模型不可靠的标准做法：事实由代码保证，语言由模型负责。

真实项目里能力表配错、路由规则写错都很常见，关键不是不犯错，而是错误能被自动发现和纠正。

（4）三条工程要点。 图上列出的三条纪律直接对应「最容易失控的模式」这个判断：

  1. 任务队列是代码的账本：状态、尝试次数、来源都记在 Task 里，这样「谁在干什么、重试了几次、钱花在哪」永远可查；
  2. 分派依据是能力表，不是名字：能力标签可校验、可配置、可审计；靠名字猜在规模变大后必然出错；
  3. 重试必须有上限：没有 max_attempts 的系统遇到永久性失败会无限烧钱；有上限之后，「放弃并转人工」变成一个有明确条件的正常分支。

def run_pipeline(task, max_revisions=2):
    calls = 0
    store = {}

    def planner(t):
        nonlocal calls
        calls += 1
        return {"steps": ["draft", "polish"]}

    def executor(plan, feedback=None):
        nonlocal calls
        calls += 1
        text = "draft of " + task
        if feedback:
            text += " | fixed: " + feedback
        return text

    def reviewer(text):
        nonlocal calls
        calls += 1
        if "fixed" in text:
            return True, "ok"
        return False, "missing fixed marker"

    plan = planner(task)
    store["plan"] = plan
    out = executor(plan)
    store["executor_0"] = out

    revisions = 0
    while True:
        ok, reason = reviewer(out)
        store["review_%d" % revisions] = {"ok": ok, "reason": reason}
        if ok or revisions >= max_revisions:
            break
        revisions += 1
        out = executor(plan, feedback=reason)
        store["executor_%d" % revisions] = out

    return {"output": out, "calls": calls, "revisions": revisions, "store": store}

import json

def run_manager(task, max_subtasks=5, max_steps=10):
    calls = 0
    steps = 0
    truncated = False

    def manager_plan(t):
        nonlocal calls
        calls += 1
        raw = json.dumps({
            "subtasks": [
                {"id": "t1", "desc": "collect sources"},
                {"id": "t2", "desc": "analyze data"},
                {"id": "t3", "desc": "write summary"},
                {"id": "t4", "desc": "extra check"},
                {"id": "t5", "desc": "extra check 2"},
                {"id": "t6", "desc": "extra check 3"},
            ]
        })
        return json.loads(raw)

    def worker(desc):
        nonlocal calls, steps
        calls += 1
        steps += 1
        return "done: " + desc

    plan = manager_plan(task)
    subtasks = plan.get("subtasks", [])
    if len(subtasks) > max_subtasks:
        subtasks = subtasks[:max_subtasks]
        truncated = True

    results = []
    for st in subtasks:
        if steps >= max_steps:
            truncated = True
            break
        results.append({"id": st["id"], "out": worker(st["desc"])})

    calls += 1  # manager 汇总
    return {
        "result": " | ".join(r["out"] for r in results),
        "stats": {"calls": calls, "steps": steps, "truncated": truncated},
    }

6.2.1 MCP 解决什么问题

在 MCP 出现之前，每个 AI 应用要接入外部工具，都要为每个工具 × 每个应用写一次适配代码：

没有 MCP：        Claude ─┬─ 数据库适配
                          ├─ 文件系统适配
                          └─ 搜索适配
                  Cursor ─┬─ 数据库适配（再写一遍）
                          ├─ 文件系统适配（再写一遍）
                          └─ 搜索适配（再写一遍）

MCP（Model Context Protocol）的做法是定义一个标准协议，把「工具提供方」和「工具使用方」解耦：

有 MCP：          工具 Server ──┐
                                 ├─ MCP 协议 ── Client A (Claude)
                  工具 Server ──┤            ── Client B (Cursor)
                  工具 Server ──┘            ── Client C (你的应用)

MCP 三个核心概念：

概念角色说明
Host发起连接的 LLM 应用如 Claude Desktop、Cursor、你的 Agent 系统
ClientHost 内部的连接器负责与某个 Server 通信
Server提供能力的服务暴露工具、资源、提示词

MCP Server 能提供什么：

  • Tools（工具）：可供模型执行的函数 ← 本课程重点
  • Resources（资源）：上下文和数据
  • Prompts（提示词模板）：可复用的工作流模板

Client 能提供什么：Elicitation（向用户索要额外信息的机制）。

6.2.2 2026-07-28 规范的核心变化：无状态化

这是本节最重要的知识点。MCP 现在是一个无状态协议。

规范原文（specification/2026-07-28/basic）： "MCP is a stateless protocol: all the information needed to process a request is contained in the request itself. A server processes each request independently; no state should be inferred from previous requests, even those on the same connection or stream."

6.2.3 请求元数据：_meta 与必需请求头

_meta 字段（请求体内）

每个请求的 params._meta 里必须包含：

键类型是否必需说明
io.modelcontextprotocol/protocolVersionstring必需如 "2026-07-28"

缺失必需字段的后果：服务器必须用 JSON-RPC 错误码 -32602（Invalid params）拒绝， HTTP 状态必须是 400 Bad Request。

HTTP 请求头（Streamable HTTP 传输）
头名来源何时必需
MCP-Protocol-Version协议版本所有 POST 请求
Mcp-MethodJSON-RPC 的 method 字段所有请求
Mcp-Nameparams.name 或 params.uritools/call、resources/read、prompts/get
Mcp-Param-{Name}工具参数（由工具的 inputSchema 里 x-mcp-header 标注）按工具定义

关键规则：头部与请求体必须一致。 服务器必须校验，不一致时返回 400 + JSON-RPC 错误码 <code>-32020</code>（HeaderMismatch）。

为什么要冗余到头部：让中间件（负载均衡、网关、可观测工具）不用解析请求体就能路由和检查。 规范原文："so that intermediaries (load balancers, gateways, observability tooling) can route and inspect requests without parsing the body." 为什么服务器必须校验一致性：这是一个真实的安全边界。如果负载均衡按头部的 Mcp-Name 做权限判断，而服务器按请求体的 params.name 执行，攻击者只要让两者不同， 就能绕过权限校验。规范原文明确说了这个场景。

值的编码规则：如果值不能安全地放进 ASCII 头部（含非 ASCII 字符、控制字符、首尾空格）， 必须用 Base64 哨兵格式：

  • 每个请求须自带版本与能力声明
  • 长连接是状态来源，故移除 GET 端点
  • 流不可续传，断了要用新请求 ID 重发

解析与常见错误：答题要点在因果链：有状态导致会话粘性与共享存储需求，无状态使任意实例可服务任意请求。代价是客户端每个请求都要携带完整元数据，且流断开后无法续传，必须用新请求 ID 重新发起。常见失分是只答好处不答客户端责任。

q06-02-05（简答 · ★★★）头部冗余与一致性校验的必要性

MCP 要求把 method、name 等信息同时放进 HTTP 头部和请求体，并要求服务器校验两者一致。 请回答：为什么要做这种冗余？为什么服务器必须校验一致性？值不能安全放进 ASCII 头部时如何处理？

提示：想想中间件为什么不想解析 body；权限判断按头部、执行按 body 会怎样

判分要点（AI 排错时逐条核对）

  • 让中间件不解析请求体即可路由与检查
  • 便于负载均衡、网关、可观测工具
  • 不校验则头部与执行体判据可被分离
  • 攻击者可借此绕过权限校验
  • 非 ASCII、控制字符、首尾空格须 Base64 哨兵
  • 格式形如 =?base64?xxx?=

解析与常见错误：冗余的目的是让中间件无需解析请求体即可路由与检查。校验一致性则是安全边界：若负载均衡按 Mcp-Name 判权而服务器按 params.name 执行，攻击者让两者不同即可绕过。编码问题用 Base64 哨兵格式解决。常见失分是忽略安全动机。

  • 三个必需头部缺一即 -32020

  • Mcp-Name 须等于 params.name

参考解（先自己写，卡住再展开）

def validate_tools_call(headers, body):
    required = ["mcp-protocol-version", "mcp-method", "mcp-name"]
    for h in required:
        if h not in headers:
            return 400, -32020

    params = body.get("params", {})
    if headers["mcp-method"] != body.get("method"):
        return 400, -32020
    if headers["mcp-name"] != params.get("name"):
        return 400, -32020

    meta = params.get("_meta", {})
    if "io.modelcontextprotocol/protocolVersion" not in meta:
        return 400, -32602
    if "io.modelcontextprotocol/clientCapabilities" not in meta:
        return 400, -32602

    return 200, None

import json

def build_response(accept_header, result, want_stream):
    accept = accept_header or ""
    if "application/json" not in accept or "text/event-stream" not in accept:
        return 406, None, None

    payload = dict(result)
    payload.setdefault("resultType", "complete")
    text = json.dumps(payload, ensure_ascii=False)

    if want_stream:
        return 200, "text/event-stream", "data: " + text + "\n\n"
    return 200, "application/json", text

6.3.2 为什么 Agent 特别需要可观测性

对比普通后端服务：

维度普通后端Agent
执行路径代码固定，路径可预测运行时决定，每次可能不同
失败原因异常栈能定位模型「想错了」不会抛异常，只会给错答案
成本基本固定随步数、上下文长度动态变化
复现同样的输入基本同样输出有随机性，必须记录完整上下文才能复现

结论：Agent 的调试不能靠断点，必须靠完整的执行轨迹记录。

6.3.3 三个层次，职责不同

层次回答什么问题粒度本课程实现
日志（Logging）刚刚发生了什么单条事件logging + 结构化字段
追踪（Tracing）整个请求经历了什么，哪步最慢最贵请求级树状结构Trace / Span（自建）或 Langfuse
评测（Evaluation）改了之后是变好还是变坏数据集级固定评测集 + 指标

  • 哪一步最慢？→ 优化目标明确；
  • 哪一步最贵？→ 通常是上下文最长的那个 LLM 调用；

6.3.6 trace_id 串联与 Prompt 版本管理：把「今天好像变差了」变成可定位的问题

6.3.3 讲了可观测性的三个层次，6.3.4 给 Agent 装上了追踪。但真实团队里最常见的对话是这一句：

这句话之所以无法处理，是因为它不可定位。这一节补上让它可定位的两样东西：贯穿全链路的 trace_id，以及可回溯的 Prompt 版本。

一、trace_id：一次请求的身份证

追踪系统里最贵的错误是「关联不上」。用户报「刚才那个答案不对」，你手上有十万条 Span，但不知道是哪一条。

规则很简单：入口生成，全程透传，落地到日志与响应头。

# code/ch06/d28/trace.py
from __future__ import annotations

import contextvars
import uuid

_current: contextvars.ContextVar[str] = contextvars.ContextVar("trace_id", default="")


def new_trace_id() -> str:
    return uuid.uuid4().hex[:16]


def set_trace_id(trace_id: str | None = None) -> str:
    value = trace_id or new_trace_id()
    _current.set(value)
    return value


def get_trace_id() -> str:
    return _current.get()

用 contextvars 而不是全局变量，原因很实际：异步服务里全局变量会被并发请求互相覆盖，而 contextvars 天然按任务隔离。

接下来是三个必接的点：

  1. 入口中间件：无论成功失败都要有 trace_id。
  2. 每一次模型调用 / 工具调用：作为属性写进 Span。
  3. 响应头：回给前端，用户截图就能对上。

二、Prompt 版本：让每次改动可归因

Agent 调优的迭代速度很快，一天改三版提示词是常态。如果没有版本号，你会遇到这个死循环：

改了提示词 → 感觉变好 → 三天后发现问题 → 想回退 → 不知道回退到哪一版

最低成本的方案不需要任何平台，就是把 Prompt 当代码管：

# code/ch06/d28/prompt_registry.py
from __future__ import annotations

import hashlib
from dataclasses import dataclass


@dataclass(frozen=True)
class PromptVersion:
    name: str
    version: str
    template: str

    @property
    def digest(self) -> str:
        return hashlib.sha256(self.template.encode("utf-8")).hexdigest()[:12]


PLANNER_V1 = PromptVersion(
    name="planner",
    version="v1",
    template="你是任务规划器。把用户目标拆成不超过 5 步，输出 JSON 数组。",
)

PLANNER_V2 = PromptVersion(
    name="planner",
    version="v2",
    template=(
        "你是任务规划器。把用户目标拆成不超过 5 步，输出 JSON 数组。\n"
        "每一步必须包含 action 与 expected_result 两个字段。"
    ),
)


def registry() -> dict[str, PromptVersion]:
    return {"planner:v1": PLANNER_V1, "planner:v2": PLANNER_V2}

三条纪律：

  1. 每次调用都把 <code>version</code> 与 <code>digest</code> 写进 Span 属性。 这样评测集一跑，你就能按版本分组看指标。
  2. 改动必须配一次评测集回归。 只有版本号没有指标，等于换了个名字继续猜。
  3. 回退是一等公民。 上一版永远留在 registry 里，回退是改一个字符串，不是翻 Git 历史。

    "按 user_id 稳定分桶：同一个用户永远看到同一版本，避免体验抖动。"
    bucket = int(hashlib.md5(user_id.encode("utf-8")).hexdigest()[:8], 16) / 0xFFFFFFFF
    return PLANNER_V2 if bucket < ratio else PLANNER_V1

为什么用 <code>user_id</code> 而不是随机数：同一个人反复切换版本会让主观反馈完全失效，也会让「这个用户说变好了」无法归因。稳定分桶是 A/B 的基本功。

四、把它串成一条排查链

import time
import json

MAX_LEN = 4000

def _safe_json(obj):
    try:
        s = json.dumps(obj, ensure_ascii=False, default=str)
    except Exception:
        s = str(obj)
    if len(s) > MAX_LEN:
        s = s[:MAX_LEN] + '...[truncated]'
    return s

class Span:
    def __init__(self, name, parent=None):
        self.name = name
        self.parent = parent
        self.children = []
        self.start = None
        self.duration = 0.0
        self.tokens = 0
        self.input = None
        self.output = None
        self.error = None

    def __enter__(self):
        self.start = time.time()
        return self

    def __exit__(self, exc_type, exc, tb):
        self.duration = time.time() - self.start
        if exc is not None:
            self.error = f'{exc_type.__name__}: {exc}'
        return False

class Tracer:
    def __init__(self):
        self.root = Span('trace')
        self.stack = [self.root]

    def span(self, name):
        parent = self.stack[-1]
        sp = Span(name, parent)
        parent.children.append(sp)
        return _SpanCtx(self, sp)

    def _notify(self, span):
        try:
            # 这里模拟上报，真实场景可能是 Langfuse
            if span.error:
                print(f'[warn] span {span.name} error: {span.error}')
        except Exception as e:
            print(f'[warn] trace notify failed: {e}')

    def report(self, span=None, depth=0):
        span = span or self.root
        line = '  ' * depth + f'- {span.name} {span.duration:.3f}s tokens={span.tokens}'
        if span.error:
            line += f' error={span.error}'
        print(line)
        for c in span.children:
            self.report(c, depth + 1)

class _SpanCtx:
    def __init__(self, tracer, span):
        self.tracer = tracer
        self.span = span

    def __enter__(self):
        self.tracer.stack.append(self.span)
        return self.span.__enter__()

        self.span.__exit__(exc_type, exc, tb)
        self.tracer.stack.pop()
        self.tracer._notify(self.span)
        return False

（2）三条最重要的工程结论：

  1. 压缩省的是 <code>prompt</code>，不是 <code>completion</code> ——所以抓手是「控制上下文长度」，不是「让模型少说点」。本次实测 prompt 显著下降，completion 完全不变。

6.4.5 语义缓存：把重复问题变成接近零成本

6.4.3 的三层护栏管的是「别失控」，但还有一个更常见的浪费：用户问的东西，你上个月已经答过了。

Agent 场景的请求分布极度长尾又极度重复——真实业务里「怎么报销」「年假几天」这类问题能占到总请求的相当比例。这一节把重复请求的成本打到接近零。

先分清三种缓存，别混用
类型命中条件命中率风险
精确缓存请求文本完全一致低（措辞一变就废）几乎无
语义缓存向量相似度超过阈值高误命中，答案张冠李戴

Agent 场景真正的收益在语义缓存，真正的危险也在语义缓存。 所以这一节的重点不是「怎么加缓存」，而是「怎么加一个不会害你的缓存」。

一、从精确缓存开始：先把地基打对
# code/ch06/d29/exact_cache.py
from __future__ import annotations

import hashlib
import json
import time


def cache_key(payload: dict) -> str:
    "稳定键：参数顺序无关。"
    normalized = json.dumps(payload, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(normalized.encode("utf-8")).hexdigest()


class ExactCache:
    def __init__(self, ttl_seconds: int = 3600) -> None:
        self.ttl = ttl_seconds
        self._store: dict[str, tuple[float, str]] = {}

    def get(self, key: str) -> str | None:
        item = self._store.get(key)
        if item is None:
            return None
        expires_at, value = item
        if time.time() > expires_at:
            del self._store[key]
            return None
        return value

    def put(self, key: str, value: str) -> None:
        self._store[key] = (time.time() + self.ttl, value)

<code>sort_keys=True</code> 不是可选项。 参数顺序不同的同一请求算出不同键，缓存命中率会莫名其妙地低——这是最常见的一个 bug。

二、语义缓存：相似度阈值是唯一起作用的旋钮
# code/ch06/d29/semantic_cache.py
from __future__ import annotations

import math
from typing import Callable, Sequence


def cosine(a: Sequence[float], b: Sequence[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    if na == 0 or nb == 0:
        return 0.0
    return dot / (na * nb)


class SemanticCache:
    def __init__(self, embed: Callable[[str], list[float]], threshold: float = 0.93) -> None:
        self.embed = embed
        self.threshold = threshold
        self._entries: list[tuple[list[float], str]] = []  # 向量, 答案

    def lookup(self, question: str) -> tuple[str | None, float]:
        query = self.embed(question)
        best_score = 0.0
        best_answer: str | None = None
        for vector, answer in self._entries:
            score = cosine(query, vector)
            if score > best_score:
                best_score, best_answer = score, answer
        if best_score >= self.threshold:
            return best_answer, best_score
        return None, best_score

    def remember(self, question: str, answer: str) -> None:
        self._entries.append((self.embed(question), answer))

class BudgetExceeded(Exception):
    def __init__(self, used, limit, over):
        self.used = used
        self.limit = limit
        self.over = over
        super().__init__(
            f"预算超支：已用 {used}，上限 {limit}，超支 {over}"
        )


class BudgetGuard:
    def __init__(self, max_tokens, max_cost=None):
        self.max_tokens = max_tokens
        self.max_cost = max_cost
        self.used_tokens = 0
        self.used_cost = 0.0

    def check(self, estimated):
        """调用前估算：预估会超就提前拒绝"""
        est_tokens = estimated.get("tokens", 0)
        est_cost = estimated.get("cost", 0.0)
        if self.used_tokens + est_tokens > self.max_tokens:
            return False
        if self.max_cost is not None and self.used_cost + est_cost > self.max_cost:
            return False
        return True

    def charge(self, usage):
        self.used_tokens += usage.get("tokens", 0)
        self.used_cost += usage.get("cost", 0.0)
        if self.used_tokens > self.max_tokens:
            raise BudgetExceeded(
                self.used_tokens, self.max_tokens,
                self.used_tokens - self.max_tokens,
            )
        if self.max_cost is not None and self.used_cost > self.max_cost:
            raise BudgetExceeded(
                self.used_cost, self.max_cost,
                round(self.used_cost - self.max_cost, 6),
            )

    g = BudgetGuard(max_tokens=100, max_cost=0.01)

class BudgetGuard:
    def __init__(self, total_budget):
        self.total_budget = total_budget
        self.used = 0
        self._logs = []

    def check(self, estimated_tokens):
        if self.used + estimated_tokens > self.total_budget:
            self._logs.append(
                f"blocked: used={self.used}, est={estimated_tokens}, "
                f"total={self.total_budget}"
            )
            return False
        return True

    def record(self, actual_tokens):
        self.used += actual_tokens

    def logs(self):
        return list(self._logs)

    print(g.check(50))   # False

def build_trace(records):
    children = {}
    for r in records:
        children.setdefault(r["parent"], []).append(r)

    lines = []

    def walk(parent, depth):
        for r in children.get(parent, []):
            lines.append("  " * depth + f"{r['name']} ({r['ms']}ms)")
            walk(r["id"], depth + 1)

    walk(None, 0)
    return "\n".join(lines)


def slowest(records):
    return max(records, key=lambda r: r["ms"])["name"]
