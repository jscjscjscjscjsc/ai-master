8.0 先回答一个关键问题：什么时候该微调？

这是本章最重要的一节，比任何代码都重要。

很多人的第一反应是「模型效果不好就去微调」。但微调是最后该考虑的手段，不是第一选择。

三种「让模型学会新知识/新行为」的手段

手段解决什么成本更新速度可解释性
Prompt 工程输出格式、语气、推理方式极低改一行即生效完全可见
RAG（第 3 章）知识：企业私有事实、时效性信息低重跑索引即可可溯源到证据
微调（本章）行为/风格/格式：稳定的输出习惯、领域语言、特定任务的模式中–高需要重新训练模型内部，不可见

决策顺序（请按这个顺序排除）

效果不好？
  │
  ├─ 是「不知道事实」吗？          → 用 RAG（第 3 章），不要微调
  │   （问了企业规章，模型答不出）      微调也能"塞"知识，但更新成本高、易幻觉、不可溯源
  │
  ├─ 是「格式不稳定」吗？          → 先加 Few-shot + Schema 校验（第 1 章）
  │   （要 JSON，偶尔多废话）          Prompt 能解决 80% 的格式问题
  │
  ├─ 是「推理能力不够」吗？        → 换更强的模型 / 用推理模型（第 1 章 Day04）
  │   （多步推理总错）                微调不会让模型变聪明
  │
  └─ 是「输出风格/模式需要高度一致」吗？
      （例如：必须用公司特有的判例书写风格输出、
        或需要极高的格式遵循率、或需要降低推理成本用更小的模型）
      → 这时候才考虑微调
一句话记住： RAG 管「知道什么」，微调管「怎么表达」，Prompt 管「这次怎么做」。 三者是互补的，不是替代关系。生产系统里三者通常同时存在。

微调的真实收益与代价

收益代价
格式遵循率显著提升（可到 95%+）需要标注数据（几百到几千条）
可以用更小的模型达到大模型的格式能力 → 降低推理成本需要 GPU 与训练知识
固定风格的输出更稳定知识会过时，且更新要重新训练
减少 Prompt 长度（行为内化到权重里）→ 省 token可能损害通用能力（灾难性遗忘）
有质量风险：训练数据里的问题会被固化
最后一条最值得警惕：微调会把训练数据里的偏见、错误、格式缺陷都学进去， 而且很难事后修正。所以数据质量比数量重要得多。

D35

Day 35｜Transformer 与 LoRA 原理

≈120 分钟 7 道练习

一、教学目标

  1. 说清注意力机制在做什么（不需要会推导，但要能用话讲清）；
  2. 理解 LoRA 为什么能大幅降低训练参数量；
  3. 能手算 LoRA 的参数量（这是面试常考题）。

二、Transformer：用一句话讲清注意力

$$\text{Attention}(Q,K,V)=\text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

用一句话解释：每个词都生成三个向量——Query（我在找什么）、Key（我能提供什么）、 Value（我的实际内容）。用 Q 和所有 K 做匹配打分，按分数加权汇总所有 V。

面试版回答（背这一段就够）：

自注意力让每个位置都能直接"看到"序列中所有其他位置， 因此能并行计算并捕捉长距离依赖，不像 RNN 必须顺序处理。 Q·K 决定"关注谁"，加权 V 决定"取回什么信息"。

为什么这决定了 LoRA 的可行性：Transformer 的参数量大头在线性层（尤其是注意力的 Q/K/V/O 投影和前馈层）。这些层就是大矩阵乘法。LoRA 正是作用在这些矩阵上。

三、LoRA：低秩假设

核心观察

微调时，权重的更新量具有低秩特性——不需要用满秩矩阵来表示这个变化。

做法

原始权重 $W_0 \in \mathbb{R}^{d \times k}$ 冻结不变，额外训练两个小矩阵：

$$W = W_0 + \Delta W = W_0 + BA$$

其中 $B \in \mathbb{R}^{d \times r}$，$A \in \mathbb{R}^{r \times k}$，且 $r \ll \min(d,k)$。

  • 初始化：$A$ 用随机高斯，$B$ 用零 → 训练开始时 $\Delta W = 0$，不破坏原模型；
  • 前向传播：$h = W_0 x + BAx$；
  • 梯度只更新 A 和 B，$W_0$ 冻结。
参数量对比（必须会算）

假设 $W_0$ 是 $4096 \times 4096$：

方案参数量相对比例
全量微调$4096 \times 4096 = 16{,}777{,}216$100%
LoRA，$r=8$$4096 \times 8 + 8 \times 4096 = 65{,}536$0.39%
LoRA，$r=16$$4096 \times 16 \times 2 = 131{,}072$0.78%
LoRA，$r=4$$4096 \times 4 \times 2 = 32{,}768$0.195%

降到 1/256（$r=16$ 时）。这就是 LoRA 的核心价值。

为什么省显存（三层原因，别只答一层）
层次原因
1. 优化器状态消失全量微调要为每个参数存 Adam 的一阶/二阶动量（2 倍参数量）；LoRA 只为 A、B 存 → 主省这里
2. 梯度消失只算 A、B 的梯度，不需要为 $W_0$ 存梯度
3. 检查点变小保存的是 adapter（几 MB），不是整个模型（几十 GB）→ 便于分发与切换
常见的错误回答：「LoRA 省显存是因为参数少」。这只说对了一半—— 真正的显存大头是优化器状态和梯度（通常是参数量的 4–12 倍）。 参数量的减少通过这两个乘数被放大。面试时能说出这一层，就是分水岭。

四、LoRA 的关键超参数

参数作用常见取值调参提示
r（秩）表达能力4 / 8 / 16 / 32任务越复杂越大；先从 8 试。PEFT 默认 <code>r=8</code>
lora_alpha缩放因子，实际更新量是 $\frac{\alpha}{r} BA$通常取 2r（如 r=8 → 16）PEFT 默认 <code>lora_alpha=8</code>（不是 16）——所以想用 2r 的惯例时必须显式写
lora_dropout防过拟合0.05–0.1（PEFT 默认 <code>0.0</code>）数据少时调大
target_modules作用在哪些层通常 Q/K/V/O 投影 + 前馈层只加在注意力层效果通常够；数据少时加太多层易过拟合
bias是否训练偏置项"none"（默认）一般不动
task_type任务类型"CAUSAL_LM"它继承自 <code>PeftConfig</code>，不是 <code>LoraConfig</code> 特有字段
<code>alpha/r</code> 这个比值才是真正的缩放系数。所以只改 r 不改 alpha 会同时改变表达能力 和有效学习率——这是新手常见的混淆点。 特别注意默认值的坑：因为 PEFT 的 lora_alpha 默认是 8（等于 r 的默认值）， 所以「默认配置」的有效缩放是 8/8 = 1。而网上教程常推荐 alpha = 2r， 那是 r=8 时 alpha=16——两者差一倍。 如果你照抄代码但只改 r，就会在不知情的情况下改变有效学习率。 显式写出 <code>r</code> 和 <code>lora_alpha</code>，永远是个好习惯。
LoRA 的三个重要增强开关（2026 年仍在 PEFT 内，不是替代品）

有一个常见误解：「LoRA 已经被 DoRA / rsLoRA / LoRA+ 取代了」。 实际上它们都是 LoRA 的增强选项，不是替代方案：

方法PEFT 中的用法关键作用
rsLoRALoraConfig(use_rslora=True)缩放因子从 alpha/r 改为 <code>alpha/√r</code>，让增大 <code>r</code> 时收益更稳定（否则大 r 反而可能变差）
DoRALoraConfig(use_dora=True)把权重分解为「幅度 + 方向」分别更新，低秩场景效果更好。限制：与 adapter_names 推理不兼容；不支持 megatron_core
LoRA+不在 <code>LoraConfig</code> 里！用 from peft.optimizers import create_loraplus_optimizer(..., loraplus_lr_ratio=16)给 A、B 用不同学习率，官方称可提速约 2 倍、性能提升 1–2%
⚠️ 最常见的代码错误：把 loraplus_lr_ratio 当成 LoraConfig 的参数传进去。 它属于优化器，不是配置对象 —— 传错会报 TypeError。
还有一个趋势值得知道：初始化方法在分化

PEFT 的 init_lora_weights 现在支持远超早期的选项： "olora"、"pissa"、"pissa_niter_[N]"、"corda"、"loftq"、"eva"、"orthogonal"、 "mica"、"lora_ga" 等。同时 peft/tuners/ 下新增了大量 LoRA 家族适配器 （delora、gralora、hira、c3a、glora、lily、miss、osf、loha、lokr、ia3、adalora 等）。

这说明生态在「分化」，而不是「收敛到某个 LoRA 取代者」。 对你的实际意义：默认用标准 LoRA 起步，遇到具体瓶颈（大 r 不稳、效果不够）再针对性换开关， 不要一上来就纠结选哪个变体。

五、动手：用 numpy 亲手实现 LoRA

python code/ch08/10_lora_from_scratch.py

这个脚本不依赖 GPU，用纯 numpy 实现并验证：

  1. 构造两个矩阵 $W_0$（冻结）和 $A, B$（可训练）；
  2. 实现前向传播 $h = W_0x + BAx$；
  3. 实现反向传播，验证 $W_0$ 的梯度确实为零（这是"冻结"的含义）；
  4. 在一个合成任务上真的训练，打印 loss 下降曲线；
  5. 计算并打印参数量对比表。

这个实验的教学价值：你会亲眼看到「只训练 0.4% 的参数，也能让 loss 降下来」。 比看一百遍公式都有用。

为什么第 3 步很重要：很多人能背出"LoRA 冻结原权重"， 但如果你没有亲手验证过 W_0 的梯度是零，你就不知道"冻结"在代码里到底是什么样的。 验证方式：反向传播后打印 W_0.grad，它应该是全零矩阵或 None。 这一个检查就能防止你把 requires_grad 设错却毫无察觉。

Day 36｜LoRA / QLoRA 微调实战

≈120 分钟 7 道练习
环境提示：本节需要 GPU。请使用 Colab（免费 T4 即可）或本地有 GPU 的机器。 课程提供的脚本 code/ch08/20_qlora_colab.py 是完整可运行版本。

一、教学目标

  1. 走通微调的完整链路：数据构造 → 配置 → 训练 → 评估 → 合并/部署；
  2. 理解 SFT 数据格式与数据质量要求；
  3. 能读懂 loss 曲线，判断训练是否正常。

二、微调链路全景

flowchart LR
    A[明确目标] --> B[构造数据集]
    B --> C[选基座模型]
    C --> D[配置 LoRA/QLoRA]
    D --> E[训练]
    E --> F[评估]

三、数据构造：SFT 格式与质量

格式
{"instruction": "把下面这段客服对话抽取成 JSON", "input": "客户说：我买的耳机左耳没声音，要退货", "output": "{\"intent\": \"退货\", \"product\": \"耳机\", \"issue\": \"左耳无声\"}"}

三种组织方式：

方式适用说明
instruction / input / output通用最常用，适配性好
纯对话格式（messages 数组）多轮对话任务与推理时格式一致
分类/生成对单一任务最简单
数据质量要求（比数量重要）
要求为什么
输出格式绝对一致微调会学走任何模式，包括你不想要的（比如有的样本带 markdown 围栏、有的不带 → 模型输出会随机带或不带）
覆盖边界情况只给正常样本，模型遇到缺失字段就乱编。要显式给"字段缺失时输出 null"的样本
不要有互相矛盾的样本同输入不同输出会让模型学成"随机选一个"
规模参考格式/风格微调通常几百到几千条足够；不要一上来就标几万条
最容易犯的错：数据里混了不同格式的样本。 比如 100 条 JSON 输出中，有 3 条是纯文本。模型学完后，约 3% 的概率输出纯文本—— 这个比例足以让你的生产系统偶发解析失败，而且极难排查（因为你在训练时根本没注意那 3 条）。

四、QLoRA：在消费级 GPU 上微调

LoRA 解决了「训练参数多」，QLoRA 进一步解决了「基座模型太大装不下」。

技术做法效果
LoRA冻结 $W_0$，只训练低秩增量训练参数量降 100–1000 倍
QLoRA把冻结的 $W_0$ 量化到 4-bit，LoRA 增量仍用较高精度训练显存再降约 4 倍

关键点：量子化只作用于冻结的基座，可训练的 LoRA 部分保持较高精度—— 这样才能保证训练效果。这是 QLoRA 的巧妙之处：它量化的是不需要梯度的那部分。

量化的四个关键参数
⚠️ 一个高频的错误归因：BitsAndBytesConfig 不在 <code>bitsandbytes</code> 包里，而在 <code>transformers</code> 里。 正确导入是 from transformers import BitsAndBytesConfig。 写成 from bitsandbytes import BitsAndBytesConfig 会直接 ImportError。 （bitsandbytes 只提供量化后端实现，配置类由 transformers 定义。）
参数含义常用值（含默认值）
load_in_4bit用 4-bit 加载基座True（默认 False）
bnb_4bit_quant_type量化数据类型"nf4"（正态浮点，比 fp4 更适合权重分布）。默认是 <code>"fp4"</code>
bnb_4bit_compute_dtype计算时用什么精度torch.bfloat16（新卡）或 float16（默认 float32，显存占用更高）
bnb_4bit_use_double_quant二次量化（量化常数本身）True（再省一点显存，默认 False）
约束：load_in_4bit 和 load_in_8bit 不能同时为 True，同时传会直接 ValueError。

五、读懂 loss 曲线

曲线形态说明处理
平稳下降后收敛正常可以停
下降后上升过拟合，或学习率太大早停 / 降低学习率 / 加数据
剧烈震荡学习率太大，或 batch 太小降学习率 / 提高梯度累积
基本不降学习率太小、数据太少、或目标任务超出模型能力检查数据质量
降到很低但效果差过拟合到训练集看验证集，不要只看训练 loss
必须做的一件事：留出验证集。 只看训练 loss 就像只看练习册答案——你无法知道模型是否真的学会了。

六、评估微调效果：不要只看「感觉更好了」

必须做对照实验：

对照组目的
基座模型（未微调）基线
基座 + 优化后的 Prompt（Few-shot）关键对照：微调是否真的比 Prompt 工程更好？
微调后模型实验组

评估指标（延续第 1 章评测器的思路）：

指标说明
格式遵循率输出能被正确解析的比例（微调最直接的收益）
任务准确率用固定测试集 + 规则评分
泛化能力用训练集里没出现过的输入测试（这是最容易被忽略、也最重要的）
通用能力是否退化用几个通用问题测一下（检查灾难性遗忘）
推理成本如果用小模型替代大模型，实际省了多少
如果「基座 + 好 Prompt」和「微调」效果差不多，那就不该微调。 这个结论看起来很朴素，但它是很多团队浪费几周时间后才得出的。

Day 37｜上下文工程与成本优化

≈120 分钟 7 道练习

一、教学目标

  1. 说清上下文工程与 Prompt 工程的区别；
  2. 掌握上下文组装、裁剪、压缩、外部化四种手段；
  3. 用真实数据做出成本优化决策。

二、上下文工程 vs Prompt 工程

Prompt 工程上下文工程
关注点单次指令怎么写整个上下文窗口里放什么
内容system prompt 的措辞system + 历史 + 检索证据 + 工具定义 + 外部记忆
时间尺度一次调用整个会话/任务的生命周期
核心问题「怎么问」「放什么、放多少、什么时候清理」

三篇权威论述（答辩引用这些，比引用博客可信得多）：

来源定义 / 核心论点
Anthropic《Effective context engineering for AI agents》(2025-09-29)定义："the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference"；与 prompt engineering 的关系："the natural progression of prompt engineering"。推荐技术：right-altitude system prompts、token-efficient 且互不重叠的工具设计、精选少量 few-shot（而非穷举边界情况）、just-in-time 检索、compaction（接近上限时摘要）、structured note-taking、sub-agent 架构
Manus《Context Engineering for AI Agents》(2025-07-18)核心论点：KV-cache 命中率是生产级 Agent 最重要的单一指标。实践："Keep your prompt prefix stable"、"Make your context append-only"、"Mask, Don't Remove"（工具按需屏蔽而非删除）、"treat the file system as the ultimate context"、压缩要设计成可恢复的（restorable）、"leave the wrong turns in the context"（保留错误，因为错误恢复是 agentic 行为的标志）
LangChain《Context Engineering for Agents》(2025-07-02)定义："the delicate art and science of filling the context window with just the right information for the next step"。四大策略：Write / Select / Compress / Isolate
这三篇里最有实践价值的两个洞察： 1. 保留错误痕迹（Manus）：把失败的工具调用从上下文里删掉，会让模型重复犯同样的错。 保留它，模型反而能"学会"绕开——这是一个反直觉但极其有用的经验； 2. KV-cache 命中率（Manus）：这意味着改动 system prompt 的开头比改动结尾代价高得多， 因为前缀一变，整个缓存失效。这直接影响你的 Prompt 版本管理策略。

上下文窗口的构成（这张图请记住，它是优化的地图）：

┌─────────────────────── 上下文窗口 ───────────────────────┐
│ 1. system prompt 与规则        ← 固定成本，必须保留        │
│ 2. 工具定义（tools schema）    ← 固定成本，工具多时很可观  │
│ 3. 检索到的证据（RAG）          ← 每次都可能变，重点优化对象 │
│ 4. 对话历史                    ← 随轮数增长，最大的变量    │
│ 5. 当前用户输入                ← 必须保留                 │
│ 6. 外部记忆的引用              ← 按需检索，不常驻          │
└───────────────────────────────────────────────────────────┘
        固定成本                可变成本（优化重点）
一个容易被忽略的成本：工具定义本身占 token。 如果你注册了 30 个工具，每个工具的 JSON Schema 可能占 100–200 token， 那就是 3000–6000 token 的固定开销，每一次调用都要付。 所以「工具太多」不只是让模型选错的概率上升，也是实打实的成本。 （解法：按场景动态加载工具子集。）

三、四种优化手段及各自代价

手段做法省 token代价适用
裁剪（Truncate）保留最近 N 轮中丢失早期信息对话类，早期内容不重要时
压缩（Summarize）早期内容摘要高有损；摘要本身要调用一次模型长任务，主线信息重要
外部化（Externalize）中间产物存外部，上下文只留引用极高Agent 需要主动查询，多一步产物大的任务（代码、长文档）
选择性检索历史不常驻，按需检索相关轮次极高检索可能漏；实现复杂超长会话

组合使用的实际方案：

system + 工具定义     → 永久保留（关键约束不可裁剪）
最近 K 轮             → 完整保留（保证当前决策质量）
更早的轮次            → 摘要为「已完成 + 关键结论」
中间产物（代码/文档）  → 外部存储，上下文只留一行引用

必须用数据回答的三个问题：

  1. 压缩从第几轮开始划算？ 关键看「累计节省的上下文 token」何时超过「摘要本身的开销」。

本实验的答案是：30 轮都还没回本。如果你的对话只有几十轮，优先用滑动窗口；

  1. 滑动窗口在什么时候开始丢关键信息？ 脚本会构造一个「早期设定、后期依赖」的场景来暴露这个问题

—— 这是滑动窗口的固有代价，它省 token 是靠牺牲记忆；

  1. 「关键约束永不裁剪」是怎么实现的？ 答案：system prompt 与用户原始需求单独保存，

不进裁剪池。无论用哪种策略，这条都必须遵守，否则 Agent 会"忘掉"最初的任务约束。

工程结论（这才是可以外推的经验，而不是具体数字）：

对话短（几十轮以内）     → 滑动窗口最划算，简单且无额外调用
对话很长（几百轮以上）   → 摘要压缩才开始划算（摘要开销被摊薄）
中间产物很大            → 用外部化（存文件/DB，上下文只留引用），这一招最省
注意：本实验的数字来自离线靶场与特定的消息长度分布。 不要照搬"30 轮不划算"这个结论 —— 你要在自己的任务和模型单价上重跑一遍。 可以外推的是分析方法：永远把「节省」和「额外开销」放在同一张表里比较。

五、成本优化的完整检查表

优化点检查什么典型收益
输出长度是否有限制？输出单价通常是输入的 2–4 倍高
工具定义是否加载了用不到的工具？中（工具多时高）
检索条数top_k 是否过大？证据是否去重？中–高（RAG 场景）
证据块大小切块是否过大？（第 3 章 Day12）中
历史管理是否每轮都重发全部历史？高（长会话）
模型选型简单任务是否用了大模型？高
缓存是否有可复用的结果（相同问题、相同文档）？视场景
批处理能批量的是否逐条调用？中
优化顺序建议：先做「高收益 + 低风险」的（输出长度、模型选型、缓存）， 再做「需要改造架构」的（历史管理、外部化）。 不要一上来就做最复杂的优化 —— 先量化，再动刀。
